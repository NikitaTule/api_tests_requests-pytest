# QIWI Wallet API - Автотесты

Фреймворк для API-тестирования QIWI Wallet на основе документации [developer.qiwi.com](https://developer.qiwi.com/ru/qiwi-wallet-personal/).

> **Важно:** QIWI API не является работающим сервисом - выпуск токенов прекращён.
> Тесты спроектированы на основе документации и демонстрируют подход к тестированию, а не результат выполнения.

## 1. Структура проекта

```
├── config/
│   ├── config.yaml          # Хосты сервисов
│   └── users.yaml           # Данные тестовых пользователей
├── services/
│   └── qiwi/
│       ├── models/          # Pydantic-модели ответов API
│       │   ├── profile.py
│       │   ├── balance.py
│       │   └── payments.py
│       ├── resources/       # Обёртки над эндпоинтами
│       │   ├── profile.py
│       │   ├── balance.py
│       │   └── payments.py
│       └── qiwi_service.py  # Точка входа в сервис
├── tests/
│   ├── profile/
│   │   └── test_profile.py  # Smoke: доступность сервиса
│   ├── balance/
│   │   └── test_balance.py  # Проверка баланса
│   └── test_payment/
│       └── test_payment.py  # Создание и исполнение платежа
├── utils/
│   ├── clients/
│   │   └── http_client.py   # Базовый HTTP клиент
│   ├── config_reader.py     # Чтение конфигурации
│   └── logger.py            # Логирование запросов
├── .env.example             # Пример переменных окружения
├── conftest.py              # Фикстуры pytest
├── pytest.ini               # Конфигурация pytest
└── requirements.txt         # Зависимости
```

**Что за что отвечает:**

- `config/` - хранит конфигурацию окружения и данные пользователей. Секреты (токен) резолвятся из `.env` через `${VAR}` синтаксис.
- `services/qiwi/resources/` - обёртки над эндпоинтами. Каждый метод выполняет один запрос и возвращает типизированную Pydantic-модель.
- `services/qiwi/models/` - Pydantic-модели, описывающие контракт API. Автоматически валидируют структуру ответа при каждом вызове.
- `services/qiwi/qiwi_service.py` - точка входа. Создаёт HTTP-клиент с нужным хостом и заголовками, инициализирует все ресурсы.
- `utils/clients/http_client.py` - базовый HTTP-клиент на основе `requests`. Поддерживает retry, логирование, работу с бинарными данными.
- `utils/config_reader.py` - читает `config/*.yaml`, резолвит переменные окружения, предоставляет доступ через атрибуты (`app_config.users.qiwi_user.wallet`).
- `utils/logger.py` - логирует все HTTP-запросы и ответы на уровнях INFO и DEBUG.
- `conftest.py` - фикстуры `user_data` и `qiwi`. Поддерживает выбор пользователя через маркер `@pytest.mark.user("user_name")`.

## 2. Запуск тестов

### Подготовка

1. Установить зависимости:
```bash
pip install -r requirements.txt
```

2. Создать `.env` файл в корне проекта:
```env
QIWI_TOKEN=your_bearer_token_here
```

Токен выдаётся вручную на [qiwi.com](https://qiwi.com/settings/apps), действует 180 дней.

### Запуск

```bash
# Все тесты
pytest tests/

# Только smoke - проверка доступности сервиса (пункт 1)
pytest tests/ -m smoke

# Только проверка баланса (пункт 2)
pytest tests/ -m balance

# Только платёжные тесты (пункты 3 и 4)
pytest tests/ -m payments

# С подробным логированием запросов
pytest tests/ --log-cli-level=DEBUG

# С подробным выводом pytest
pytest tests/ -v
```

## 3. Архитектура

Фреймворк построен по паттерну **Service Object + Resource Layer**:

```
conftest (фикстуры)
    └── QiwiService (сервис)
            ├── Profile (ресурс)  →  ProfileResponse (модель)
            ├── Balance (ресурс)  →  BalanceResponse (модель)
            └── Payments (ресурс) →  PaymentHistoryResponse / CreatePaymentResponse / TransactionResponse
```

**Почему такая архитектура:**

**HttpClient** - единственная точка выполнения HTTP-запросов. Вся логика retry, логирования и обработки ответов сосредоточена в одном месте. При смене библиотеки (например с `requests` на `httpx`) меняется только этот файл.

**Resource layer** - каждый ресурс отвечает за один логический блок API. Методы принимают только бизнес-параметры, скрывая детали HTTP. Тест не знает про эндпоинты, заголовки и тело запроса.

**Pydantic-модели** - автоматическая валидация контракта API при каждом вызове. Если структура ответа изменилась - тест упадёт на десериализации, не на assert. Это значит что структурные регрессии обнаруживаются без написания дополнительных проверок.

**QiwiService** - инкапсулирует создание клиента с нужным хостом и заголовками. Все ресурсы получают один и тот же клиент. Добавление нового ресурса - одна строка в сервисе.

**Преимущества при масштабировании:**
- Новый эндпоинт - добавляем метод в нужный ресурс, не трогая тесты
- Новый пользователь - добавляем в `users.yaml`, указываем маркер `@pytest.mark.user("new_user")` в тесте
- Новое окружение - меняем хост в `config.yaml`, остальное не трогаем
- Новый сервис - создаём папку в `services/`, добавляем фикстуру в `conftest.py`

## 4. Обоснование тестовых решений

### Пункт 1 - Проверка доступности сервиса

Доступность сервиса можно трактовать на двух уровнях:

**Технический уровень** - сервер жив и отвечает на запросы. Достаточно любого GET на домен.

**Бизнесовый уровень** - сервис жив и его основные функции работают корректно. Сервер может отвечать 200 но платежи не ходить, баланс не отдаваться, профиль не читаться. Для финансового продукта это и есть недоступность.

Выбран бизнесовый уровень - smoke проверяет все ключевые блоки сервиса:

**`test_get_profile`** - авторизация работает, сервис узнаёт пользователя. Без этого недоступны все остальные операции.

**`test_get_balance`** - финансовый блок отвечает. Независимый домен - может упасть отдельно от профиля.

**`test_create_payment`** и **`test_execute_payment`** - core функция продукта работает. Если деньги не ходят - сервис недоступен по своему основному назначению.

Все smoke тесты не проверяют бизнес-значения - только структуру ответа через Pydantic. Это намеренно: smoke должен быть стабильным независимо от состояния данных конкретного пользователя.

### Пункт 2 - Проверка баланса

**`test_balance_is_positive`** - проверяет что на рублёвом счёте (`currency == 643`) есть средства. Используется `pytest-check` для мягких ассертов: сначала проверяем что рублёвый счёт найден, затем что баланс больше 0. Если первый assert упал - второй всё равно выполняется, что даёт полную картину проблемы.

### Пункт 3 - Создание платежа

**`test_create_payment`** - отправляет перевод на 1 рубль и проверяет два условия: наличие `transaction.id` в ответе и статус `Accepted`. Используется `pytest-check` - оба условия проверяются независимо. `transaction.id` нужен для последующей проверки исполнения.

### Пункт 4 - Исполнение платежа

**`test_execute_payment`** - проверяет что платёж реально исполнен, а не просто записан в систему. Тест делает две проверки:

- Статус транзакции `SUCCESS` через `GET /v1/transactions/{txnId}` - подтверждает что платёж прошёл полный цикл обработки
- Баланс после платежа меньше баланса до - подтверждает что деньги реально списаны

Проверка только статуса была бы недостаточной - статус может быть `SUCCESS` при ошибке списания. Изменение баланса является финальным доказательством исполнения платежа.
